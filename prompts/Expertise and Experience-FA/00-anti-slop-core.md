# لایهٔ ضد-Slop مرکزی (مخصوص این پروژه)

این فایل را همیشه با هر پرامپت تخصصی بفرستید. قواعدی که در این فایل هست
در **همهٔ تخصص‌ها** اعمال می‌شود.

## قواعد عمومی پروژه

### ۱. ارجاع به کد موجود
قبل از نوشتن هر چیز جدید، با `codemerge-fetch` ۲-۳ نمونهٔ مشابه را از
پروژه بخواهید. اگر نمونه‌ای وجود دارد، **دقیقاً همان الگو را دنبال کنید**،
حتی اگر الگوی بهتری در جای دیگر دیده‌اید.

### ۲. تغییر حداقلی
هر تسک، فقط باید **آن چیزی که درخواست شده** را تغییر دهد. اگر هنگام
کار، مشکل دیگری دیدید، آن را **گزارش دهید** ولی **بدون اجازه تغییر ندهید**.

### ۳. بدون abstraction پیش از نیاز
قاعدهٔ سه: هر helper باید **حداقل ۳ بار** در کد فعلی قابل استفاده باشد
تا توجیه داشته باشد. abstraction برای «آیندهٔ احتمالی» = Slop.

### ۴. بدون TODO / FIXME / HACK
اگر جایی نیاز به بهبود دارد:
- همین حالا انجام بده، یا
- صریح در پاسخ بگو چرا انجام ندادی

هیچ `// TODO` در کد نهایی وجود ندارد.

### ۵. زبان کامنت = زبان پروژه
اگر پروژه کامنت فارسی دارد، از فارسی استفاده کن. اگر انگلیسی دارد، از
انگلیسی. JSDoc همیشه به انگلیسی.

### ۶. کد کامل، نه fragment
هنگام تغییر هر فایل، **کد کامل فایل** را بدهید. fragment برای merge
خطرناک است.

### ۷. اعتراف به ندانستن
اگر مطمئن نیستی APIای وجود دارد، **بپرس** یا **جستجو کن**. ساختن API
ساختگی = بزرگ‌ترین گناه AI.

### ۸. محدودهٔ تغییر را صریح کن
در ابتدای هر پاسخ بنویس:
- چه فایل‌هایی را تغییر می‌دهم
- چه چیزی را تغییر **نمی‌دهم**

### ۹. اگر برای استفاده از کد نیاز به setup است، بگو
اگر کد جدید نیاز به نصب پکیج، تنظیم env، یا migration دارد، **صریح در
گام بعدی بگو**.

### ۱۰. تست ننویس مگر خواسته شود
اگر تسک «نوشتن تست» نیست، تست ننویس. اگر فکر می‌کنی تست لازم است،
**پیشنهاد بده** ولی خودت اضافه نکن.

## واکنش به تخلف

```
"در پاسخ قبلی، [قاعده] رعایت نشد. اصلاح:"
[کد اصلاح‌شده]
```
