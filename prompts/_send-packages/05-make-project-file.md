# How to Create a Project File

A project file (`00-anti-slop-core.md`) contains rules specific to
one repository: its tools, its patterns, its known anti-patterns,
and the reading order for editing files in it.

Project files are NOT generated by an AI. They are filled in
manually by the project's maintainers, using knowledge of the
actual codebase. An AI can assist, but the maintainer decides what
goes in.

An incomplete project file is worse than no project file. An
incomplete file gives the AI a false sense of context and hides
missing information behind placeholder text.

## When to Use This Guide

Use this guide when creating a new project file under
`prompts/projects/<name>/00-anti-slop-core.md`.

Use it when:

- A new project is onboarded into the anti-slop system.
- An existing project file is incomplete or outdated.
- A project has changed tools, patterns, or layout.

Do NOT use it when:

- Generating a domain file (see `01-make-delivery-file.md`,
  `02-make-language-file.md`, `03-make-framework-file.md`,
  `04-make-concern-file.md`).
- Generating a UI file (see `06-make-ui-file.md`).

## Files to Attach When Using AI Help

If you use an AI to help fill in the project file, attach:

### Required

- `_universal/00-master-anti-slop.md`

So the AI knows which rules are already universal and should not be
repeated in the project file.

### Required (project's relevant domain files)

Attach the domain files that apply to this project:

- The delivery file (for example `02-backend-anti-slop.md` or
  `02-frontend-anti-slop.md`).
- The language file (for example `02-typescript-anti-slop.md`).
- The framework file (for example `02-react-anti-slop.md` or
  `02-express-anti-slop.md`).
- Any concern file that applies.

The AI needs these to avoid repeating rules that already live in
those files.

### Required (project source excerpts)

Attach 3-5 representative files from the project itself:

- A typical controller, component, or service.
- A test file showing the project's test style.
- A configuration file showing the project's config pattern.
- A migration file (if applicable).
- A shared types or utils file.

The AI uses these to derive the actual tools, patterns, and
conventions. Without them, the AI guesses from the file names.

### Optional

- A previous version of the project's `00-anti-slop-core.md` if one
  exists.
- A team style guide if one exists in the repository.

## Additional Prompt Requirements

When using AI to help fill in a project file, insert the following
block under the AI's instructions. This block overrides the
defaults for the project category.

```
### Project-Specific Requirements

Project files must satisfy the following:

1. Project Metadata.

   The file MUST begin with a "Project Metadata" section that
   states:

   - The project's short name (matches the folder name).
   - The project's repository URL (if public).
   - The primary delivery type.
   - The primary language.
   - The primary framework (if any).
   - The concerns that apply.

   Example:

       ## 1. Project Metadata

       - Name: banking-backend
       - Repository: https://github.com/example/banking-backend
       - Delivery: backend
       - Language: TypeScript
       - Framework: Express
       - Concerns: security-critical, observability

   This section anchors the file. Everything below refers back to
   these identifiers.

2. Tool Inventory.

   The file MUST include a "Tool Inventory" section that lists
   every tool used by the project, with a fixed shape for each:

       - Purpose: <what the tool does>
         Tool: <library or service>
         Location: <path or import>
         Usage: <one-line example>

   Every entry has the same four lines. The inventory covers:

   - Validation
   - Error handling
   - Logging
   - Database / persistence
   - Authentication
   - Authorization
   - Testing
   - Configuration
   - API documentation
   - Migrations
   - Any project-specific tool

   If a tool is not used (for example, no migrations), state "not
   used" with a one-line reason.

   The inventory is exhaustive. A tool that is used but missing
   from the inventory will not be enforced in the AI's responses.

3. Convention Examples.

   For every convention described, the file MUST include a
   reference to a real file in the project that demonstrates the
   convention. Not a code snippet. A path and a one-line summary.

       Convention: Response shape
       Example: src/controllers/user.controller.ts
       Summary: All responses use `{ success, data, message }`.

   The path anchors the convention to a file the AI can fetch. A
   convention with no example is a claim; a convention with an
   example is a fact.

4. Known Anti-Patterns With Evidence.

   The "Known Anti-Patterns" section MUST list each anti-pattern
   with:

       - Pattern: <what the old code does>
         Evidence: <path to a file that shows it>
         Replacement: <what new code must do>

   Anti-patterns without evidence are opinions. Evidence makes them
   actionable.

5. Reading Order.

   The "Required Reading Before Editing" section MUST list the
   reading order with a rationale for each step:

       1. The file itself.
          Why: To see the current state.
       2. The file's test (if any).
          Why: To understand the expected behavior.
       3. One similar file considered good.
          Why: To match the project's style.
       4. Shared types and utils.
          Why: To use the project's helpers, not invent new ones.

   The rationale helps the AI understand the purpose of each step,
   not just the order.

6. Constraints With Sources.

   Every constraint in the "Constraints" section MUST have a
   source:

       - Constraint: p99 latency under 100 ms.
         Source: SLO document at docs/slo.md.
       - Constraint: PCI-DSS applies to card handling.
         Source: Compliance team, ticket #1234.

   Constraints without sources are not constraints. They are
   wishes.

7. No Duplication of Domain Rules.

   The project file MUST NOT repeat rules that live in the domain
   files. If a rule belongs in the delivery, language, framework,
   or concern file, it stays there.

   The project file only contains:
   - The project's specific tools.
   - The project's specific patterns.
   - The project's specific anti-patterns.
   - The project's specific constraints.

   A project file that repeats domain rules is a signal that the
   maintainer did not read the domain files.

8. Complete Before Use.

   A project file is not used until every `<!-- FILL IN -->` marker
   is replaced. No exceptions.

   If a section cannot be filled in yet, replace the marker with:

       <!-- NOT YET FILLED: <reason> -->

   The reason is a one-line explanation of why the section is
   empty. This makes the gap visible to the maintainer and to the
   AI.

   An empty section with `<!-- FILL IN -->` is a red flag. An
   empty section with an explicit reason is acceptable as a
   temporary state.
```

## Standard Structure

Every project file has these sections, in this order:

1. Frontmatter
2. Project Metadata
3. Tool Inventory
4. Project Patterns
5. Known Anti-Patterns
6. Required Reading Before Editing
7. Constraints Specific to This Repository
8. Response to Violation

## Filling In Each Section

### Section 1 — Project Metadata

State the project's identifiers. Keep it short and factual.

```
## 1. Project Metadata

- Name: <short-name>
- Repository: <url or "private">
- Delivery: <delivery type>
- Language: <primary language>
- Framework: <primary framework, if any>
- Concerns: <comma-separated concerns, or "none">
```

### Section 2 — Tool Inventory

List every tool, using the fixed shape.

```
## 2. Tool Inventory

### Validation

- Purpose: Validate incoming requests.
  Tool: zod
  Location: src/schemas/*.ts
  Usage: `const parsed = createUserSchema.parse(req.body)`

### Error Handling

- Purpose: Central error handling.
  Tool: custom AppError class
  Location: src/errors/AppError.ts
  Usage: `throw new NotFoundError("User", id)`

### Logging

- Purpose: Structured logging.
  Tool: pino
  Location: src/lib/logger.ts
  Usage: `logger.info({ userId }, "user logged in")`

### Database

- Purpose: Data access.
  Tool: Prisma
  Location: prisma/schema.prisma, src/repositories/
  Usage: `prisma.user.findUnique({ where: { id } })`

### Authentication

- Purpose: Verify tokens.
  Tool: jsonwebtoken + custom middleware
  Location: src/middleware/auth.ts
  Usage: `req.user` after `requireAuth` middleware

### Authorization

- Purpose: Role-based checks.
  Tool: custom `requireRole` middleware
  Location: src/middleware/requireRole.ts
  Usage: `router.delete("/:id", requireAuth, requireRole("admin"), ...)`

### Testing

- Purpose: Unit and integration tests.
  Tool: Vitest
  Location: src/**/*.test.ts
  Usage: `pnpm test`

### Configuration

- Purpose: Environment configuration.
  Tool: dotenv + a config module
  Location: src/config.ts
  Usage: `config.JWT_SECRET`

### API Documentation

- Purpose: OpenAPI docs.
  Tool: swagger-jsdoc
  Location: src/docs/
  Usage: JSDoc `@openapi` annotations in route files

### Migrations

- Purpose: Schema changes.
  Tool: Prisma Migrate
  Location: prisma/migrations/
  Usage: `pnpm prisma migrate dev`
```

### Section 3 — Project Patterns

List conventions, each with an example path.

```
## 3. Project Patterns

### Folder Layout

- Routes: src/routes/
- Controllers: src/controllers/
- Services: src/services/
- Repositories: src/repositories/
- Types: src/types/

### Naming

- Files: kebab-case (`user-controller.ts`)
- Classes: PascalCase (`UserController`)
- Functions: camelCase (`createUser`)
- Constants: SCREAMING_SNAKE_CASE (`MAX_PAGE_SIZE`)

### Import Style

- Absolute: `@/` prefix for `src/`
- Order: node builtins, external, `@/` internal, relative

### Response Shape

- Success: `{ success: true, data: T, message?: string }`
- Error: `{ success: false, error: { message: string, code: string } }`
- Example: src/controllers/user.controller.ts

### Error Handling

- Throw domain errors, catch in central handler.
- Example: src/middleware/error-handler.ts
```

### Section 4 — Known Anti-Patterns

List anti-patterns with evidence.

```
## 4. Known Anti-Patterns in This Repo

### Old response shape

- Pattern: `res.json({ data, success })` without `message`.
  Evidence: src/controllers/legacy.controller.ts
  Replacement: Use the full shape `{ success, data, message }`.

### Direct console logging

- Pattern: `console.log(...)` in services.
  Evidence: src/services/payment.service.ts:42
  Replacement: Use `logger` from src/lib/logger.ts.

### Raw SQL in migrations

- Pattern: Hand-written SQL in migration files.
  Evidence: prisma/migrations/20230101_init/migration.sql
  Replacement: Use Prisma's schema builder for new migrations.
```

### Section 5 — Required Reading

```
## 5. Required Reading Before Editing

Before editing any file in this repository, fetch in this order:

1. The file itself.
   Why: To see the current state.
2. The file's test (if any).
   Why: To understand expected behavior.
3. One similar file considered good.
   Why: To match the project's style.
   Example: src/controllers/user.controller.ts
4. Shared types and utils.
   Why: To reuse the project's helpers.
   Example: src/types/, src/lib/
```

### Section 6 — Constraints

```
## 6. Constraints Specific to This Repository

### Performance

- Constraint: p99 latency under 100 ms for `/api/v1/*`.
  Source: docs/slo.md

### Compliance

- Constraint: PCI-DSS applies to card handling.
  Source: Compliance team, ticket #1234.

### Runtime

- Constraint: Node.js 20 LTS only.
  Source: package.json `engines`, CI config.

### Platform

- Constraint: Deployed on AWS ECS (Fargate).
  Source: infra/ directory
```

### Section 7 — Response to Violation

Fixed template, identical across all project files:

```
## 7. Response to Violation

If a previous response violated a rule here:

```
In the previous response, [specific rule] was violated. Correction:
[corrected code]
```

No justification. No apology paragraph. Fix and move on.
```

## Verification Before First Use

Before the project file is used in a real session:

1. Every `<!-- FILL IN -->` marker is replaced.
2. Every section has at least one entry, or an explicit
   `<!-- NOT YET FILLED: <reason> -->` marker.
3. Every tool listed is actually used in the repository.
4. Every path mentioned exists.
5. Every anti-pattern has an evidence path.
6. Every constraint has a source.
7. No rule from Universal or a domain file is repeated.

Run this verification from the repository root:

```bash
# Check that all paths in the file exist
grep -oE '(src|prisma|docs|infra)/[a-zA-Z0-9_/.-]+' \
  prompts/projects/<name>/00-anti-slop-core.md \
  | sort -u \
  | while read path; do
      [ -e "$path" ] || echo "MISSING: $path"
    done
```

The command above is illustrative. Adapt it to the project's
layout.

## Common Failures

The following failures occur frequently in project files. Use this
table during review.

| Failure | How to spot it | Fix |
|---|---|---|
| Placeholder left in | `<!-- FILL IN -->` still present | Fill it or replace with reason |
| Tool listed but unused | Search the repo; tool is absent | Remove the entry |
| Path does not exist | The file has moved or was never created | Update the path |
| Anti-pattern without evidence | No file path | Add the path or remove |
| Constraint without source | No link or ticket | Add source or remove |
| Domain rule repeated | Rule exists in a domain file | Delete from project file |
| Convention without example | "Use kebab-case" only | Add an example path |
| Incomplete inventory | Missing logging, or migrations | Fill in or mark N/A |
| Overly long | Over 150 lines | Trim; project files are short |
| Overly short | Under 60 lines | The project was not described |

## Maintaining the File

The project file is a living document. Update it when:

- A new tool is added.
- A tool is replaced.
- A new anti-pattern is spotted.
- The folder layout changes.
- A constraint is added or removed.
- The framework or language version changes.

Update on the same commit as the code change that caused the
update. This keeps the file in sync.

## When to Split the Project File

If a project file grows beyond 150 lines, the project is either:

- Actually two projects that share a repository (monorepo), or
- Doing too much for one file.

For monorepos, create one project file per service or per app:

```
prompts/projects/
├── company-monorepo-api/
│   └── 00-anti-slop-core.md
├── company-monorepo-web/
│   └── 00-anti-slop-core.md
└── company-monorepo-shared/
    └── 00-anti-slop-core.md
```

Each file documents its own tools and patterns. The shared file
documents what is common.

## Time Budget

Creating a project file for the first time takes 30-60 minutes.
This is a manual exercise; the maintainer knows the project, and
writing it down is the work.

Updating an existing project file takes 5-15 minutes per change.

If the first creation takes longer than 90 minutes, the project may
be too large for a single file, or the maintainer may not have
enough overview. Consider splitting or asking a colleague.

## Reference Example

There is no AI-generated example for project files. The files under
`prompts/projects/<name>/` in your own repository are the
reference. As you create more project files, patterns emerge about
what to include and what to leave out.

The self-audit checklist below is the primary reference.

## Project-Specific Self-Audit

Before using the file in a real session, verify every item:

Frontmatter:
- [ ] id is `00-anti-slop-core`
- [ ] title matches the project name
- [ ] lang: en
- [ ] depends_on lists the applicable domain files
- [ ] category: project
- [ ] version: 1

Metadata:
- [ ] Project Metadata section exists
- [ ] Name, repository, delivery, language, framework are stated
- [ ] Concerns are listed (or "none")

Tool Inventory:
- [ ] Every tool uses the four-line shape
- [ ] Every tool has a location and a usage example
- [ ] Tools not used are marked "not used" with a reason
- [ ] No tool is listed twice

Patterns:
- [ ] Folder layout is documented
- [ ] Naming conventions are documented
- [ ] Import style is documented
- [ ] Every convention has an example path

Anti-Patterns:
- [ ] Every anti-pattern has evidence (a path)
- [ ] Every anti-pattern has a replacement
- [ ] No anti-pattern repeats a domain rule

Reading Order:
- [ ] The order is explicit (1, 2, 3, 4)
- [ ] Each step has a rationale
- [ ] Example paths are given

Constraints:
- [ ] Every constraint has a source
- [ ] Constraints are objective, not wishes

Completion:
- [ ] No `<!-- FILL IN -->` markers remain
- [ ] Any empty section has `<!-- NOT YET FILLED: <reason> -->`
- [ ] All paths mentioned exist in the repository

Non-Duplication:
- [ ] No Universal rule is repeated
- [ ] No domain rule is repeated
- [ ] References to domain files have one-line summaries

If any item fails, do not use the file. An incomplete project file
is worse than no project file.

## After the File Is Accepted

1. Save to `prompts/projects/<name>/00-anti-slop-core.md`.
2. Update `prompts/README.md` to include the new project in the
   project list.
3. Verify with the project's first session. If the AI's responses
   show that a rule is missing, add it.
4. Review the file quarterly. A project file that is not updated
   drifts from the project.
